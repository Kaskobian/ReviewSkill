# AI-Generated Code Review Guide

> Review checklist for AI-assisted and AI-generated code: hallucinated APIs, dependency risk, plausible-but-wrong logic, over-engineering, test mirroring, and provenance.

AI-generated code compiles, reads fluently, and is often wrong in ways fluent prose hides. The failure mode is **plausibility without verification**: the model produces what code *usually* looks like, not what *this* codebase and *these* dependency versions actually do. Review it with the same four-phase process as any change, plus the checks below.

Severity labels follow the skill standard: 🔴 `[blocking]` · 🟡 `[important]` · 🟢 `[nit]`.

---

## 1. Hallucinated APIs and Imports

Models invent function names, parameters, and whole modules that look real. Every imported symbol must exist **in the pinned version** of the dependency — not in a newer version, not in a different library, not in the model's training data.

```python
# ❌ Hallucinated: pandas has no read_excel_safe; plausible name, nonexistent API
df = pd.read_excel_safe("report.xlsx", sanitize=True)

# ✅ Verify against the installed version's actual API
df = pd.read_excel("report.xlsx")
```

```javascript
// ❌ Hallucinated: lodash has no deepMergeWith; mixes real naming conventions
import { deepMergeWith } from "lodash";

// ✅ Use the real API (or a verified alternative)
import { merge } from "lodash";
```

**Verification steps:**
1. Check the import resolves: run the project's type checker / linter / build, or grep the dependency's source in `node_modules`, site-packages, or the vendor directory.
2. Check the signature: parameter names, order, defaults, and return type against the installed version's docs or source.
3. Check version-sensitive APIs: a method added in v3 does not exist in the v2 the lockfile pins.

🔴 A hallucinated API that reaches a runtime path is blocking — it is a guaranteed crash, not a style issue.

## 2. Dependency Risk: Typosquatting and Slopsquatting

AI tools suggest package names from memory. Two failure patterns:

- **Typosquatting:** a near-miss of a real package (`reqeusts`, `lodash-es5`, `python-dateutil2`) that an attacker registered to catch exactly this mistake.
- **Slopsquatting:** a package name the model hallucinates consistently enough that attackers register it. The name looks plausible, has no history, and may contain install-time malware.

```json
// ❌ New dependency added by an AI suggestion — never verified
{
  "dependencies": {
    "express-rate-limiter": "^1.0.0"
  }
}

// ✅ The real, established package (verified on the registry)
{
  "dependencies": {
    "express-rate-limit": "^7.0.0"
  }
}
```

**For every new or renamed dependency, verify:**
- [ ] The package exists on the official registry under **exactly** that name (check character by character against the intended package)
- [ ] It has credible history: download counts, publish dates, linked source repository, known maintainers
- [ ] The source repository matches the registry listing (not a lookalike fork)
- [ ] The version exists and the lockfile was regenerated by the package manager — not hand-edited
- [ ] Install scripts (`postinstall`, `setup.py` side effects) were inspected for network calls, credential access, or obfuscated code
- [ ] The license is compatible with the project
- [ ] The dependency is actually needed — models often add a package for something the standard library or an existing dependency already does

🔴 An unverified new dependency is blocking until verified. A confirmed typosquat/slopsquat is blocking and should be reported to the security team.

See also: [Security Review Guide](security-review-guide.md) for the broader supply-chain checklist.

## 3. Plausible-but-Wrong Logic

The most dangerous category: code that looks correct, passes a casual read, and fails on real inputs. Common shapes:

```python
# ❌ Inverted boundary — reads naturally, excludes the last element
def paginate(items, page, size):
    start = page * size
    return items[start : start + size - 1]

# ✅ Half-open slice, no off-by-one
def paginate(items, page, size):
    start = page * size
    return items[start : start + size]
```

```javascript
// ❌ Silently swallows the error path
async function fetchOrNull(url, opts = {}) {
  try {
    return await fetch(url, opts);
  } catch {
    return null; // caller cannot distinguish "empty" from "failed"
  }
}

// ✅ Explicit contract: propagate or wrap, never silently null
async function fetchOrThrow(url, opts = {}) {
  const res = await fetch(url, opts);
  if (!res.ok) throw new Error(`HTTP ${res.status} for ${url}`);
  return res;
}
```

**Hunt specifically for:**
- Off-by-one in slices, loops, pagination, and buffer sizes
- Inverted or swapped conditions (`&&` vs `||`, `<` vs `<=`, negation drift)
- Wrong defaults: `0`, `""`, `None` treated as "unset" when they are valid values
- Error paths that swallow, return `null`, or log-and-continue where the contract requires failure
- Unit mismatches: seconds vs milliseconds, bytes vs characters, UTC vs local time
- Concurrency code with no actual synchronization (a `lock` variable that is never acquired)
- Regex that matches the example in the comment but not the stated requirement

**Technique:** for each non-trivial function, trace one happy path and two hostile inputs (empty, maximal, malformed) by hand. AI code frequently handles the demonstrated example and nothing else.

🔴 Logic errors on reachable paths are blocking. 🟡 Missing edge-case handling is important.

## 4. Over-Engineering and Reinvention

Models generalize from patterns, not from this codebase's needs. Typical results:

- An interface + factory + strategy for a problem with one implementation
- A new utility that duplicates an existing helper two directories away
- Configuration options nobody asked for ("flexibility" that is really untested surface area)
- Abstract base classes with a single subclass

```typescript
// ❌ Three layers of indirection for one behavior
interface DataFetcher { fetch(id: string): Promise<Data>; }
class ApiDataFetcher implements DataFetcher { /* ... */ }
class DataFetcherFactory { static create(): DataFetcher { return new ApiDataFetcher(); } }

// ✅ The codebase already has one fetch path — use it directly
const data = await api.getData(id);
```

**Check:**
- [ ] Search the repo for existing utilities before accepting a new one (see [Universal Quality Guide](code-quality-universal.md), reuse audit)
- [ ] Every abstraction has at least two real consumers or a stated, concrete reason
- [ ] New configuration options correspond to actual requirements
- [ ] The change follows the codebase's existing conventions (naming, error handling, file layout) instead of importing a generic "best practice" style

🟡 Unnecessary abstraction is important (maintenance cost). 🟢 Style drift is a nit.

## 5. Test Mirroring

AI-generated tests often assert that the code does what the code does — they mirror the implementation instead of testing the specification. Such tests pass even when the logic is wrong, and break on every harmless refactor.

```python
# ❌ Mirrors the implementation: recomputes the same (possibly wrong) formula
def test_discount():
    assert calculate_discount(100, 0.2) == 100 * (1 - 0.2)

# ✅ Asserts the specified behavior with an independently known answer
def test_discount():
    assert calculate_discount(100, 0.2) == 80
```

**Check:**
- [ ] Expected values are independently derived (from the spec, a worked example, or a known-good oracle) — not recomputed with the same logic under test
- [ ] At least one test would fail if the core logic were inverted or removed
- [ ] Edge cases from the requirements appear as tests, not just the happy path
- [ ] Mocks stand in for boundaries (network, clock, DB), not for the logic under test

Full treatment: [Test Quality Guide](test-quality-review.md).

🔴 A change whose only tests mirror the implementation has effectively no tests — treat as missing coverage.

## 6. Security Defaults

Generated code optimizes for "works in the demo", which regularly means:

- Authorization checks omitted (authentication present, ownership/role checks absent)
- CORS set to `*`, TLS verification disabled, `eval`/`exec` on input
- Secrets or connection strings hardcoded as "examples" that ship
- SQL built by string concatenation because the example in the prompt was simple
- Debug endpoints, verbose error bodies, or stack traces left enabled

```python
# ❌ "Example" credential that will ship to production
client = boto3.client("s3", aws_access_key_id="AKIAIOSFODNN7EXAMPLE",
                      aws_secret_access_key="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY")

# ✅ Credentials come from the environment / role, never from source
client = boto3.client("s3")
```

Run the full [Security Review Guide](security-review-guide.md) checklist on AI-generated changes — the base rate of missing authz and injection flaws is higher than in human-written code reviewed by its author.

🔴 Any secret in source, missing authorization, or injection vector is blocking.

## 7. Provenance and Licensing

Models reproduce training data, sometimes verbatim:

- [ ] Large distinctive blocks (unusual algorithms, long comment prose, unique naming) — check whether they match a known GPL/AGPL or proprietary source before accepting
- [ ] Vendored snippets carry their required attribution and license text
- [ ] Generated assets (images, fonts, data) have a clear license story
- [ ] The PR description discloses AI assistance where team policy requires it

🟡 Unclear provenance on substantial copied blocks is important until resolved.

## Review Checklist

### Verification (run before verdict)
- [ ] 🔴 Build / type check / linter run — hallucinated imports surface here first
- [ ] 🔴 Every new API call checked against the pinned dependency version
- [ ] 🔴 Every new dependency verified on the registry (name, history, source, license)
- [ ] 🔴 Lockfile regenerated by the package manager, consistent with the manifest

### Logic
- [ ] 🔴 Happy path + two hostile inputs traced by hand for each non-trivial function
- [ ] 🔴 Boundaries, conditions, defaults, units, and error paths checked
- [ ] 🟡 Edge cases from the requirements handled, not just the demonstrated example

### Fit
- [ ] 🟡 No reinvented utilities — repo searched for existing equivalents
- [ ] 🟡 Every abstraction earns its layers (≥2 consumers or concrete reason)
- [ ] 🟢 Conventions match the surrounding codebase

### Tests & Security
- [ ] 🔴 Tests assert specified behavior with independently derived expectations
- [ ] 🔴 At least one test fails if the core logic breaks
- [ ] 🔴 Full security checklist applied (authz, injection, secrets, CORS, TLS)

### Provenance
- [ ] 🟡 Substantial copied blocks checked for license compatibility
- [ ] 🟢 AI-assistance disclosure per team policy

## Quick Detection Heuristics

| Signal | Likely problem | First check |
|--------|---------------|-------------|
| Fluent comments restating the code | Mirroring / shallow logic | Trace hostile inputs |
| Unusually generic names (`DataProcessor`, `handleData`) | Over-engineering | Count real consumers |
| A dependency you have never heard of | Slopsquatting | Registry lookup, exact name |
| Perfect happy-path tests, no edge cases | Test mirroring | Invert the logic mentally |
| "Example" credentials or `TODO: secure this` | Security defaults | Security guide checklist |
| API you cannot find in the pinned docs | Hallucination | Grep the installed source |
